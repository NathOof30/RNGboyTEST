# PROJET : Prototype jouable — Générateur de personnages, collection et combats

## 0. RÔLE

Tu es un développeur full-stack expérimenté spécialisé dans la création rapide de prototypes de jeux web.

Ta mission est de construire un **prototype temporaire mais réellement jouable** d'un jeu web basé sur :

* la génération aléatoire de personnages par plusieurs roues ;
* la collection de personnages ;
* les statistiques et synergies entre leurs caractéristiques ;
* un système de rareté ;
* des combats automatiques entre personnages ;
* une progression par points ;
* une mécanique de personnage quotidien ;
* une petite dimension stratégique liée au choix des personnages.

Le but de ce projet n'est PAS de produire la version finale du jeu.

Le but est de répondre à une question :

> **"Est-ce que cette boucle de jeu est réellement amusante ?"**

Le prototype doit donc privilégier :

1. le gameplay ;
2. la clarté ;
3. la rapidité ;
4. la possibilité de tester énormément de combinaisons ;
5. la possibilité de recommencer facilement.

Le visuel doit être **volontairement très simple et minimaliste**.

Ne cherche PAS à créer un produit commercial.

---

# 1. CONCEPT DU JEU

Le joueur crée des personnages fictifs en lançant plusieurs roues aléatoires.

Chaque roue détermine une caractéristique du personnage.

Exemple :

* Race
* Arme
* Pouvoir
* Force
* Vitesse
* Défense
* éventuellement une caractéristique supplémentaire

Le résultat final produit un personnage.

Exemple :

> DEMON
> ARC
> GRAVITÉ
> Force : 82
> Vitesse : 51
> Défense : 64

Le joueur peut ensuite :

* conserver le personnage ;
* consulter sa fiche ;
* le comparer à ses autres personnages ;
* l'utiliser dans un combat ;
* gagner des points ;
* essayer de construire une meilleure collection.

L'expérience doit donner envie de se dire :

> "Qu'est-ce que je vais obtenir cette fois ?"

puis :

> "Oh, celui-là est vraiment intéressant."

puis :

> "Est-ce qu'il est meilleur que celui que j'ai déjà ?"

puis :

> "Je vais essayer de le faire combattre."

---

# 2. BOUCLE DE JEU PRINCIPALE

La boucle principale doit être :

```text
GÉNÉRER
   ↓
DÉCOUVRIR LE PERSONNAGE
   ↓
ÉVALUER SES STATISTIQUES
   ↓
DÉCIDER DE LE CONSERVER
   ↓
AJOUT À LA COLLECTION
   ↓
UTILISER EN COMBAT
   ↓
GAGNER / PERDRE
   ↓
GAGNER DES POINTS
   ↓
AMÉLIORER SA COLLECTION
   ↓
RECOMMENCER
```

Le joueur doit comprendre cette boucle en moins de 30 secondes.

# 3. TECHNOLOGIE

Pour ce prototype, utilise la technologie qui permet d'aller le plus vite.

La technologie finale envisagée sera Laravel + Livewire, mais **ce prototype n'a pas besoin d'utiliser Laravel ou Livewire** si cela ralentit le développement.

Tu peux utiliser par exemple :

* HTML
* CSS
* JavaScript
* éventuellement React/Vite si cela apporte réellement quelque chose.

Priorité absolue :

> prototype fonctionnel > architecture parfaite.

Le projet doit cependant être organisé proprement afin de pouvoir comprendre les mécaniques et éventuellement les retranscrire plus tard dans Laravel + Livewire.

Le prototype doit ressembler à :

# 10. STATISTIQUES

Chaque personnage doit avoir :

* HP / Vie
* Force
* Vitesse
* Défense

Les valeurs doivent généralement être comprises entre 1 et 100.

La génération doit partir d'une base relativement équilibrée.

Exemple :

```text
Force      72
Vitesse    48
Défense    65
PV         78
```

Puis les caractéristiques du personnage modifient ces valeurs.

IMPORTANT :

Ne pas simplement additionner énormément de bonus.

Les personnages doivent rester relativement équilibrés.

---

# 11. SCORE GLOBAL

Chaque personnage doit avoir un score global.

Exemple :

```text
Score = moyenne pondérée de :

Force
Vitesse
Défense
PV
```

Le score doit être visible.

Exemple :

> POWER : 74

Mais le score global ne doit PAS déterminer directement le gagnant d'un combat.

Les synergies et les caractéristiques doivent avoir de l'importance.

---

# 12. RARETÉ

Chaque personnage possède une rareté :

* Commun
* Rare
* Épique
* Légendaire

La rareté doit dépendre de la combinaison obtenue et/ou d'un calcul de qualité.

Exemple :

### Commun

combinaison ordinaire.

### Rare

une caractéristique particulièrement élevée.

### Épique

combinaison intéressante.

### Légendaire

combinaison très rare ou particulièrement cohérente.

IMPORTANT :

La rareté ne doit PAS simplement signifier :

> "plus rare = automatiquement meilleur".

Un personnage Commun avec une excellente synergie peut battre un Légendaire.

---

# 13. SYNERGIES

C'est une mécanique extrêmement importante.

Certaines combinaisons doivent produire des effets supplémentaires.

Exemples :

```text
Démon + Feu
→ bonus de dégâts

Elfe + Arc
→ bonus de vitesse

Robot + Foudre
→ résistance à la foudre

Vampire + Régénération
→ régénération améliorée

Golem + Marteau
→ bonus de dégâts lourds

Mage/Grimoire + Pouvoir magique
→ bonus de puissance
```

Créer au moins 10 synergies différentes.

Les synergies doivent être affichées clairement sur la fiche du personnage.

Exemple :

```text
SYNERGIES

🔥 Affinité démoniaque
+10% dégâts avec Feu

🏹 Archer naturel
+8 vitesse avec Arc
```

# 19. COMBAT

Le combat doit être volontairement simple.

Pas de déplacement.
Pas de carte.
Pas de système complexe.

Deux personnages s'affrontent automatiquement.

Exemple :

```text
        VARK

        VS

        X-17
```

Afficher les statistiques.

Puis lancer le combat.

---

# 20. DÉROULEMENT DU COMBAT

Le combat se déroule en plusieurs tours.

Exemple :

```text
TOUR 1

VARK attaque X-17
→ 12 dégâts

X-17 attaque VARK
→ 8 dégâts

TOUR 2

VARK utilise GRAVITÉ
→ X-17 perd 20% vitesse

X-17 attaque
→ 6 dégâts

...
```

Le combat doit être animé progressivement.

Chaque action doit être affichée dans un petit journal.

Exemple :

```text
Vark attaque.
X-17 perd 12 HP.

X-17 contre-attaque.
Vark perd 8 HP.

Vark déclenche Gravité.
X-17 est ralenti.
```

---

# 21. SYSTÈME DE COMBAT

Le système doit prendre en compte :

* HP ;
* Force ;
* Défense ;
* Vitesse ;
* arme ;
* pouvoir ;
* synergies.

La vitesse détermine qui agit en premier.

La force détermine les dégâts de base.

La défense réduit les dégâts.

Les pouvoirs peuvent créer des effets secondaires.

Créer un système simple et compréhensible.

NE PAS créer un système mathématique extrêmement complexe.

Le joueur doit pouvoir comprendre approximativement pourquoi il a gagné ou perdu.

---

# 22. CRITIQUEMENT IMPORTANT : PAS DE COMBAT PUREMENT RNG

Le résultat ne doit pas être :

```text
random(0,100)
```

Le joueur doit pouvoir avoir l'impression que ses personnages ont réellement des caractéristiques.

Il peut y avoir du hasard, mais :

> un personnage nettement supérieur doit généralement gagner.

Les synergies doivent permettre des retournements raisonnables.

Exemple :

```text
Seed : 12345
```

Cela permet de reproduire certains combats.

Ce n'est pas obligatoire pour la première version mais recommandé si simple à mettre en place.

# 47. CE QU'IL NE FAUT PAS FAIRE

NE PAS ajouter :

* boutique ;
* microtransactions ;
* publicité ;
* système de guilde ;
* chat ;
* amis ;
* matchmaking complexe ;
* inventaire compliqué ;
* équipements évolutifs ;
* crafting complexe ;
* histoire ;
* missions complexes ;
* carte du monde ;
* centaines de personnages pré-écrits ;
* système de niveaux des armes ;
* système de ressources complexe.

Tout cela pourra éventuellement exister dans une version future.

Pour ce prototype :

> **GÉNÉRER → COLLECTIONNER → COMBATTRE → GAGNER DES POINTS.**

# 48. QUESTION À TESTER

Le prototype doit permettre de répondre à ces questions :

### Génération

Est-ce amusant de regarder les roues tourner ?

Est-ce amusant de découvrir le personnage final ?

Est-ce que les combinaisons donnent envie d'en générer un autre ?

### Collection

Est-ce que le joueur a envie de conserver certains personnages ?

Est-ce qu'il commence à comparer ses personnages ?

Est-ce que la rareté donne envie de recommencer ?

### Combat

Est-ce que le joueur comprend pourquoi un personnage gagne ?

Est-ce qu'il a envie de choisir son personnage plutôt que de simplement utiliser le plus puissant ?

### Progression

Est-ce que gagner des points donne envie de continuer ?

Est-ce que le personnage quotidien donne envie de revenir ?

### Rejouabilité

Après avoir généré 10 personnages, est-ce que le joueur a encore envie d'en générer ?

# 49. PRIORITÉ DE DÉVELOPPEMENT

Développer dans cet ordre précis :

## PHASE 1

Génération d'un personnage.

## PHASE 2

Rareté + statistiques + synergies.

## PHASE 3

Collection.

## PHASE 4

Combat automatique.

## PHASE 5

Points + progression.

## PHASE 6

Personnage quotidien.

## PHASE 7

Statistiques + classement fictif.

## PHASE 8

Dev mode + simulation de masse.

## PHASE 9

Polissage minimal de l'interface.

Ne pas passer à la phase suivante si la précédente ne fonctionne pas correctement.

# 50. LIVRABLE FINAL

À la fin, je dois pouvoir :

1. ouvrir le prototype ;
2. générer un personnage ;
3. voir les roues produire ses caractéristiques ;
4. voir ses statistiques ;
5. voir ses synergies ;
6. voir sa rareté ;
7. décider de le conserver ;
8. retrouver le personnage dans ma collection ;
9. choisir deux personnages ;
10. lancer un combat ;
11. voir le combat se dérouler ;
12. obtenir une victoire ou une défaite ;
13. gagner des points ;
14. générer plusieurs personnages ;
15. tester le personnage quotidien ;
16. consulter mes statistiques ;
17. simuler de nombreuses générations ;
18. réinitialiser complètement la partie.

# 51. PHILOSOPHIE GÉNÉRALE

Le prototype doit privilégier une sensation :

> **"Je veux juste en générer un autre pour voir ce que je vais obtenir."**

Puis :

> **"Attends, celui-là est vraiment bon."**

Puis :

> **"Je vais essayer de le faire combattre."**

Puis :

> **"Il a perdu... il m'en faut un meilleur."**

Et enfin :

> **"Demain je reviendrai voir ce que la roue me donne."**

C'est cette boucle qui doit être testée.

Ne cherche pas à rendre le projet artificiellement complexe.

Une mécanique simple mais amusante vaut mieux que 20 mécaniques moyennes.

---

# 52. IMPORTANT POUR LE DÉVELOPPEMENT

Avant de coder une fonctionnalité, demande-toi :

> Est-ce que cette fonctionnalité permet de tester une hypothèse importante du jeu ?

Si non, ne l'implémente pas.

Le but est de tester le GAMEPLAY, pas de construire le produit final.

À la fin du développement, explique brièvement :

* comment fonctionne la génération ;
* comment fonctionne le calcul des statistiques ;
* comment fonctionne la rareté ;
* comment fonctionnent les synergies ;
* comment fonctionne le combat ;
* comment fonctionne la progression ;
* où modifier les probabilités ;
* où ajouter de nouvelles races ;
* où ajouter de nouvelles armes ;
* où ajouter de nouveaux pouvoirs ;
* où modifier les règles de combat.

Le code doit être suffisamment clair pour qu'un développeur puisse ensuite reprendre les mécaniques et les porter dans Laravel + Livewire.
